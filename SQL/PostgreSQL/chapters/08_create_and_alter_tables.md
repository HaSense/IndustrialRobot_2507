# 8장 테이블 생성과 변경

6장에서 정한 관계와 7장에서 고른 타입을 이제 PostgreSQL이 직접 검사할 수 있는 테이블로 만듭니다. 테이블 정의는 단순한 저장 상자가 아니라 허용할 데이터와 거부할 데이터를 선언하는 실행 가능한 설계 문서입니다. 이 장을 마치면 이후 모든 SQL 실습이 사용하는 공통 스키마가 준비됩니다.

> **실행 주체**  
> 이 장의 DDL(Data Definition Language)은 데이터베이스 소유자인 `task_admin`으로 실행합니다. 생성 스크립트는 기존 객체를 자동 삭제하지 않으며 최초 1회 실행용입니다.

## 이 장에서 배울 내용

- `CREATE TABLE`로 열, 타입과 기본값을 정의한다.
- `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`를 적용한다.
- Identity 열로 자동 번호를 생성한다.
- 참조 관계에 맞는 삭제 동작을 선택한다.
- `ALTER TABLE`로 열과 제약조건을 안전하게 변경한다.
- 테이블 정의를 확인하고 삭제 전 영향을 점검한다.

## 1. CREATE TABLE의 기본 구조

테이블 정의는 열 정의를 쉼표로 구분하고 마지막 항목 뒤에는 쉼표를 두지 않습니다.

```sql
CREATE TABLE department (
    department_id bigint GENERATED BY DEFAULT AS IDENTITY,
    department_code varchar(20) NOT NULL,
    name varchar(100) NOT NULL,
    created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT department_pk PRIMARY KEY (department_id)
);
```

문장을 실행한 역할이 테이블 소유자가 됩니다. 이 책에서는 제약조건 이름을 `<테이블>_<대상>_<종류>` 형식으로 명시합니다.

```text
department_pk
department_code_uq
app_user_department_fk
project_date_order_ck
```

오류 메시지에 이름이 나타나 어떤 규칙을 위반했는지 빠르게 찾을 수 있습니다.

## 2. 기본값과 NOT NULL

`DEFAULT`는 `INSERT`에서 열을 생략했을 때 사용할 값을 정합니다. 기존 행을 자동으로 고치는 규칙은 아닙니다.

```sql
is_active boolean NOT NULL DEFAULT TRUE,
created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
```

`NOT NULL`은 값이 반드시 있어야 한다는 뜻입니다. 빈 문자열 `''`은 NULL이 아니므로 이름과 본문에는 별도 `CHECK`도 둡니다.

```sql
CONSTRAINT department_name_not_blank_ck CHECK (btrim(name) <> '')
```

`CHECK` 결과가 `TRUE`이거나 `UNKNOWN`이면 행이 허용됩니다. 따라서 필수 열은 `CHECK`만 쓰지 말고 `NOT NULL`도 함께 선언해야 합니다.

## 3. Identity 자동 증가 열

```sql
department_id bigint GENERATED BY DEFAULT AS IDENTITY
```

Identity는 PostgreSQL이 연결된 시퀀스에서 다음 번호를 공급하는 SQL 표준 방식입니다.

- `GENERATED ALWAYS`: 일반 `INSERT`에서 직접 값 지정 거부
- `GENERATED BY DEFAULT`: 값을 생략하면 생성하고 필요하면 명시적 값도 허용

이 책은 데이터 이관과 복원 실습의 유연성을 위해 `BY DEFAULT`를 사용합니다. 번호는 행 수를 뜻하지 않으며 롤백이나 충돌로 중간 값이 비는 것이 정상입니다. Identity와 시퀀스의 자세한 동작은 19장에서 다룹니다.

## 4. UNIQUE와 PRIMARY KEY

기본 키는 행을 식별하고 자동으로 `NOT NULL`과 고유성을 적용합니다.

```sql
CONSTRAINT app_user_pk PRIMARY KEY (user_id)
```

업무상 중복되면 안 되지만 기본 키는 아닌 값에는 `UNIQUE`를 사용합니다.

```sql
CONSTRAINT app_user_email_uq UNIQUE (email)
```

`project_member`는 관계의 두 열을 묶은 복합 기본 키를 사용합니다.

```sql
CONSTRAINT project_member_pk PRIMARY KEY (project_id, user_id)
```

같은 사용자가 같은 프로젝트에 두 번 참여하는 일을 데이터베이스가 막습니다. 기본 키와 `UNIQUE`에는 고유 B-tree 인덱스가 자동 생성되므로 같은 열에 중복 인덱스를 만들지 않습니다.

## 5. FOREIGN KEY와 삭제 정책

외래 키는 참조 대상 행이 실제로 존재하도록 보장합니다.

```sql
CONSTRAINT app_user_department_fk FOREIGN KEY (department_id)
    REFERENCES department (department_id) ON DELETE RESTRICT
```

이 모델은 감사 기록 보존을 우선하므로 핵심 관계에 `ON DELETE RESTRICT`를 명시합니다. 참조 중인 부서, 사용자, 프로젝트와 업무를 먼저 지울 수 없습니다.

주요 삭제 동작은 다음과 같습니다.

| 동작 | 의미 | 사용 판단 |
|---|---|---|
| `RESTRICT` | 참조 행이 있으면 부모 삭제 거부 | 현재 핵심 모델 |
| `CASCADE` | 부모 삭제 시 자식도 삭제 | 수명 주기가 완전히 같을 때만 |
| `SET NULL` | 부모 삭제 시 외래 키를 NULL로 | 관계가 선택이고 이력 의미가 유지될 때 |
| `NO ACTION` | 기본 동작, 검사 시점 차이 가능 | 명시성을 위해 여기서는 `RESTRICT` 사용 |

외래 키는 참조되는 열의 인덱스를 활용하지만 참조하는 열에 인덱스를 자동 생성하지 않습니다. 실제 조회 패턴과 삭제 비용을 확인해 17장에서 필요한 인덱스를 추가합니다.

## 6. CHECK로 업무 규칙 표현

허용 상태값은 `CHECK ... IN`으로 제한합니다.

```sql
CONSTRAINT task_status_ck CHECK (
    status IN ('todo', 'in_progress', 'blocked', 'done', 'cancelled')
)
```

두 열 사이의 규칙도 검사할 수 있습니다.

```sql
CONSTRAINT project_date_order_ck
    CHECK (end_date IS NULL OR end_date >= start_date)
```

완료 상태와 완료 시각은 함께 변해야 합니다.

```sql
CONSTRAINT task_completed_time_ck CHECK (
    (status = 'done' AND completed_at IS NOT NULL)
    OR (status <> 'done' AND completed_at IS NULL)
)
```

`CHECK`는 같은 행의 값에 적합합니다. 다른 테이블의 현재 데이터를 조회하는 조건은 사용하지 않습니다. 예를 들어 프로젝트 관리자가 `project_member`에도 존재하는지는 이 장의 단순 제약만으로 완성하지 않고 후속 트랜잭션·트리거 설계에서 다룹니다.

## 7. 생성 순서

외래 키가 참조하는 부모 테이블을 먼저 만듭니다.

```text
department
  → app_user
    → project
      → project_member
      → task
        → task_comment
        → task_history
```

`task.parent_task_id`는 자기 테이블을 참조하므로 `task` 정의 안에서 선언할 수 있습니다.

## 8. 공통 스키마 생성

기존 테이블이 없는지 먼저 확인합니다.

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_type = 'BASE TABLE'
ORDER BY table_name;
```

처음 환경이면 0행입니다. 기존 7개 테이블이 보인다면 생성 파일을 재실행하지 말고 10절의 검증만 수행합니다.

스크립트는 전체 DDL을 `BEGIN`과 `COMMIT`으로 묶습니다. 중간 문장이 실패하면 `ON_ERROR_STOP`으로 중단되고 트랜잭션이 커밋되지 않아 일부 테이블만 남는 상태를 피할 수 있습니다.


## 9. 테이블 정의 확인

`psql`에서 한 테이블을 자세히 확인합니다.

```text
\d+ task
```

열, 타입, NULL 허용, 기본값, 인덱스, `CHECK`와 외래 키가 표시됩니다. 전체 테이블은 다음 메타 명령으로 확인합니다.

```text
\dt+
```

이식 가능한 `information_schema` 조회도 사용합니다.

```bash
psql -X -v ON_ERROR_STOP=1 -h localhost -U task_admin \
  -d task_management -W -f examples/08_check_schema.sql
```

테이블이 7행인지, 각 테이블에 `PRIMARY KEY`가 있는지, `project_member`에 두 외래 키가 있는지 확인합니다.

## 10. ALTER TABLE

운영 중 요구사항이 바뀌면 테이블을 삭제하고 다시 만드는 대신 `ALTER TABLE`을 사용합니다. 핵심 모델을 흔들지 않도록 임시 테이블에서 연습합니다.

```sql
CREATE TEMP TABLE alter_practice (
    practice_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title varchar(100) NOT NULL
);

ALTER TABLE alter_practice
    ADD COLUMN note text;

ALTER TABLE alter_practice
    ALTER COLUMN note SET DEFAULT '메모 없음';

ALTER TABLE alter_practice
    RENAME COLUMN note TO description;

ALTER TABLE alter_practice
    ADD CONSTRAINT alter_practice_title_ck CHECK (btrim(title) <> '');
```

```text
\d alter_practice
```

열 삭제는 그 데이터를 복구하기 어려우므로 영향 확인 뒤 수행합니다.

```sql
ALTER TABLE alter_practice DROP COLUMN description;
DROP TABLE alter_practice;
```

임시 테이블은 세션 종료 시에도 자동 삭제됩니다.

### 기존 데이터가 있을 때의 변경 순서

NULL이 있는 열에 바로 `SET NOT NULL`을 적용하면 실패합니다.

```text
1. 새 열을 NULL 허용으로 추가
2. 기존 행의 값을 채움
3. NULL 행이 없는지 조회
4. 기본값과 NOT NULL 적용
```

대용량 테이블의 타입 변경과 기본값 추가는 잠금과 테이블 재작성 가능성을 검토해야 합니다. 이 책에서는 18장과 26장의 동시성·실행 계획 지식을 갖춘 뒤 운영 변경을 다룹니다.

## 11. 이름 변경

## 13. 원리 이해: 제약조건의 검사 시점

`INSERT`와 `UPDATE`가 행을 바꿀 때 PostgreSQL은 타입, `NOT NULL`, `CHECK`, 고유성과 외래 키를 검사합니다. 하나라도 실패하면 해당 SQL 문은 성공하지 않습니다.

```text
입력값 → 타입 변환 → 행 제약 → 고유성 → 참조 무결성 → 저장
```

트랜잭션으로 묶은 생성 스크립트는 스키마 자체에도 전부 성공하거나 전부 취소되는 성질을 적용합니다. 단, `CREATE DATABASE`처럼 트랜잭션 안에서 실행할 수 없는 명령은 5장처럼 별도로 실행해야 합니다.

## 14. 주의 및 오류 해결

### `relation ... already exists`

생성 스크립트를 재실행했거나 같은 이름의 객체가 있습니다. `\dt`와 `\d 객체명`으로 구조를 확인합니다. `IF NOT EXISTS`로 무조건 건너뛰면 기존 구조가 올바른지는 보장되지 않으므로 검증 파일을 사용합니다.

### `permission denied for schema public`

`task_app`으로 DDL을 실행했을 가능성이 큽니다. `SELECT current_user;`로 확인하고 소유자 `task_admin`으로 다시 접속합니다.

### `violates foreign key constraint`

참조할 부모 행이 없거나 참조 중인 부모를 삭제하려 했습니다. 오류에 표시된 제약조건 이름을 스키마 파일에서 찾아 관계를 확인합니다.

### `violates check constraint`

상태 코드, 날짜 순서, 공백 문자열 또는 완료 시각 규칙을 위반했습니다. 제약을 제거하기 전에 입력이 업무 규칙에 맞는지 먼저 확인합니다.

### `cannot drop table ... because other objects depend on it`

부모 테이블부터 삭제했습니다. 오류의 의존 객체를 확인하고 자식부터 역순으로 삭제합니다. 편의를 위해 즉시 `CASCADE`를 붙이지 않습니다.

## 17. 핵심 정리

- `CREATE TABLE`은 타입과 업무 규칙을 함께 선언합니다.
- 기본값은 열을 생략할 때 적용되고 `NOT NULL`은 값의 존재를 강제합니다.
- 공백 문자열은 NULL이 아니므로 필요한 경우 `CHECK`로 막습니다.
- Identity는 자동 번호를 제공하지만 연속된 행 수를 보장하지 않습니다.
- 기본 키는 행 식별, `UNIQUE`는 후보 키의 중복 방지를 담당합니다.
- 외래 키는 부모 행의 존재를 보장합니다.
- 현재 모델은 이력 보존을 위해 핵심 관계에 `RESTRICT`를 사용합니다.
- `ALTER TABLE` 전에는 기존 데이터와 잠금 영향을 확인합니다.
- 삭제는 의존 관계의 역순으로 수행하고 `CASCADE`를 습관적으로 사용하지 않습니다.

## 18. 확인 문제

1. `DEFAULT`와 `NOT NULL`은 어떻게 다른가요?
2. `CHECK`만으로 NULL을 항상 거부할 수 없는 이유는 무엇인가요?
3. `BY DEFAULT` Identity와 `ALWAYS` Identity의 차이는 무엇인가요?
4. 외래 키의 참조하는 열에는 인덱스가 자동 생성되나요?
5. 기존 열에 `NOT NULL`을 추가하기 전에 무엇을 확인해야 하나요?
6. `DROP TABLE ... CASCADE`를 주의해야 하는 이유는 무엇인가요?
